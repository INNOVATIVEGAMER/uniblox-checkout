Checkout & Rewards Service

How the system is built, which rules it must never break, and where each rule is enforced. Every open question is decided. The decision log records who made each call: Product for product and behaviour calls, Review for technical calls taken from the architect, SDE2 and tester reviews.

Core bet

Use Postgres to enforce correctness: row locks, conditional updates and constraints. The application code orchestrates, and the database guarantees. The same design holds with one instance or ten.

Payments, modelled honestly

Checkout reserves stock and the coupon, calls a fake gateway outside any transaction, then confirms or releases. An unknown outcome is held. A reservation is released only once the gateway confirms that no charge can land.

Changes in v4

These are the fixes from the v3 review. None of the three reviewers found a correctness hole in the core design.

  • The key's state column is gone. Once committed, every key has exactly one replay source: its order, or its stored response. That removes completeKey, two CHECKs, the REQUEST_IN_PROGRESS code, and the one key-lock exception in the lock order. A retry while a payment is in flight now gets a truthful 202 with the orderId, not a 409.
  • Stock-holding orders trigger recovery. Checkout and PUT also recover stale orders that hold a product the request needs, so a stuck payment can't cause a final INSUFFICIENT_STOCK.
  • The coupon preview returns the checkout error for a reserved or redeemed coupon, so it never shows a total that checkout would reject.
  • Wiring: createDb(config) builds the pool, and createApp({ config, gateway, db }) passes it to router factories with explicit dependencies. Error codes are defined once, in an ERRORS table. Coupon codes use an uppercase alphabet and one shared schema.
  • Failure rules: reconcile and phase 0 continue past a failure on one order. 503 is listed on every route that can wait on a lock. The real-PSP mapping creates the PaymentIntent before confirming it.
  • Tests:
    • The lock timeout is long by default, and only T15 and T17 use a short one.
    • A holdLock helper makes the 503 test possible.
    • T11 and T12 now assert what tells correct code from broken code.
    • Stub-gateway recovery tests are added.
    • An it.each covers the storage rule for every checkout code.
    • Barriers are added to T4, T8 and T9.
    • Losers settle before the idle-in-transaction check.

Data model

Money is an integer number of paise (INR), stored as bigint and read with Drizzle { mode: 'number' }. Cart, order and coupon IDs are UUIDs. Product IDs are readable slugs. Every status column is NOT NULL with a CHECK listing its values. Every timestamp defaults to the database's now().

  • The discount CHECK: Postgres integer division truncates, and for non-negative values that equals floor, so the CHECK matches the money function exactly.
  • The partial unique indexes must be indexes, not table constraints. In Drizzle: uniqueIndex('orders_live_cart_uq').on(t.cartId).where(sql`${t.status} <> 'failed'`). Read the generated SQL before committing the migration.
  • A key with neither source exists only inside its own uncommitted claim. Step 8 sets order_id, a final failure stores the response, and anything else rolls the row back. "At least one source" can't be a CHECK, because the row is inserted before either exists.
  • Cart items store no price: a cart's prices are always live, and the snapshot happens once, on the order.

State machines

Cart
open: reserve :pending_payment: paid :checked_out
pending_payment: declined or abandoned :open

A business failure during reserve leaves the cart open. A decline reopens it with its items intact, so the client can fix it and pay again with a new key. The cart can be changed only while it is open. There is no expiry state (deferred).

Order
pending_payment: approved :paid
pending_payment: declined, or cancelled by recovery :failed

An order exists only once reserve succeeds. failed orders are kept for audit and excluded from revenue and milestones. paid and failed are terminal (I13). A "successfully placed order" means status = 'paid'.

Coupon
available: reserve :reserved: paid :redeemed
reserved: declined or abandoned :available

The coupon always moves together with the order that holds it (I8). A coupon is never lost to a checkout that fails.

  • available is stock >= quantity right now.
  • The cart's totalPaise is exactly what checkout will accept as expectedTotalPaise. Without a coupon it equals the subtotal. With one, the preview succeeds only for an available coupon, and otherwise returns the same error checkout would.
  • Checked-out carts still list their lines at live prices. orderId points to the order that recorded what was charged.

Why PUT to set a quantity, and an idempotent DELETE Product

"Add 1 keyboard" sent twice because of a timeout produces 2 keyboards. "Set the keyboard quantity to 1" sent twice still produces 1. A DELETE of a line that is already gone returns 200 with the cart, for the same reason. Every cart mutation is retry-safe, so only checkout needs an explicit key. The README maps the brief's "add" and "change" to PUT. The 201/200 split comes from an UPDATE … RETURNING, made while the cart lock is held, followed by an INSERT when it matched no row.

The checkout flow

The pattern: idempotency keys with atomic phases

This is the shape Stripe uses, as written up by Brandur Leach. Atomic phases are local transactions placed between calls to a foreign system: here, reserve and finalize around the gateway charge. Stock and the coupon are held as a reservation, then confirmed or released by a compensating step (a single-process saga, sometimes called Try/Confirm/Cancel).

Our pending recovery is a reconciler. Brandur's completer rolls forward by re-driving the charge from a recovery point. Ours asks the gateway what happened, then rolls forward if the charge was approved, or cancels and rolls back if it wasn't. We roll back rather than re-drive because the payment token is never stored. The pending_payment order row is the durable record of the intent to charge, so a crash at any point leaves something recovery can resolve.

Checkout is one synchronous request in three phases. The payment call sits between two transactions, because a network call must never hold row locks, and a charge must never happen inside a transaction that could still roll back. Both transactions run at READ COMMITTED. Every explicit row lock is FOR NO KEY UPDATE: we only ever update non-key columns, and this mode doesn't block the FOR KEY SHARE lock that FK inserts take (for example, adding a lamp to a cart while another cart checks a lamp out). The one stronger lock is implicit: step 8 sets the UNIQUE order_id on the request's own key row, which takes FOR UPDATE on a row no other transaction can see yet.

Phase 0: before any transaction
  1. Parse the params, the idempotency-key header and the body with zod. couponCode goes through the shared couponCodeSchema (trim, uppercase), so save10-… and SAVE10-… are the same request.
    400 VALIDATION_ERROR or 400 IDEMPOTENCY_KEY_INVALID. Nothing is stored, so the key stays unused.
  2. Recover stale pending orders on this cart, holding this coupon, or holding any product in this cart (see Pending recovery). This never runs inside a transaction. If recovering one of these orders fails, the failure is logged and checkout continues. Its own checks then decide the response.
Phase 1: reserve (transaction 1, reservePhase(db, input, key, hash))
  1. Claim the key: INSERT … ON CONFLICT (key) DO NOTHING RETURNING key. An empty result means a conflict. A request racing on the same key waits here until the first one's transaction ends. Because this is the first statement, a waiting request holds no other lock.
    On a conflict, load the row in a separate statement, which then sees the committed row. Hash differs: 422 IDEMPOTENCY_KEY_REUSED. Has an order: replay it from its current state. Has a stored response: replay that response. Nothing was written, so roll back and return.
  2. Open a savepoint, then lock the cart with FOR NO KEY UPDATE.
    Missing: 404 CART_NOT_FOUND final. checked_out: 409 CART_CHECKED_OUT final, with orderId. pending_payment: 409 CART_PAYMENT_PENDING transient, with orderId.
  3. Load the lines.
    None: 422 CART_EMPTY final.
  4. Lock the products: SELECT … WHERE id = ANY($1) ORDER BY id FOR NO KEY UPDATE. Postgres takes the row locks after the sort, so they are taken in ID order.
    Any line where stock < quantity: 409 INSUFFICIENT_STOCK final, with details: [{ productId, requested, available }] for every short line. This stays final even when another payment that is still in flight holds the units. Only cart and coupon holds are transient.
  5. Price the cart at the current prices, using money.ts.
  6. Coupon (if given): lock it by code.
    Unknown: 422 COUPON_INVALID final. redeemed: 409 COUPON_ALREADY_REDEEMED final. reserved: 409 COUPON_RESERVED transient.
  7. Price guard: the required expectedTotalPaise must equal the computed total.
    409 PRICE_CHANGED final, with details: { subtotalPaise, discountPaise, totalPaise }.
  8. Write: decrement stock, insert the pending_payment order and its line snapshots, set the coupon to reserved, set the cart to pending_payment, and set key.order_id. Release the savepoint and commit.

final errors roll back the savepoint, store toErrorBody(err) on the key, commit, and only then are returned. That is what makes a business failure the key's final answer, and the savepoint guarantees that none of reserve's writes survive with it. transient errors, a 500 and a 503 roll back the whole transaction, key claim included, so the same key can be retried. Each code's status and final flag are defined once, in the ERRORS table in errors.ts.

const outcome = await db.transaction(async (tx) => {
  const claim = await claimKey(tx, key, hash);          // throws 422, or returns a replay
  if (claim.kind === 'replay') return claim;
  try {
    const order = await tx.transaction((sp) => reserve(sp, input, key));   // savepoint
    return { kind: 'reserved', order };
  } catch (err) {
    if (!(err instanceof AppError) || !err.final) throw err;               // rolls back the claim too
    await completeKeyWithError(tx, key, err);
    return { kind: 'rejected', error: err };
  }
});
if (outcome.kind === 'rejected') throw outcome.error;   // after COMMIT
Phase 2: charge (no transaction, no connection held)
  1. A zero total (a 100% coupon) skips the gateway and counts as approved, with no payment_ref. Otherwise, call gateway.charge({ orderId, amountPaise, paymentToken }, AbortSignal.timeout(GATEWAY_TIMEOUT_MS)). The result is approved, declined(reason), or unknown (any thrown error, including the timeout).
Phase 3: finalize (transaction 2)
  1. Approved or declined: finalizeOrder(orderId, resolution), the same function recovery uses:
    Read the order's cart_id, which never changes. Lock the cart. Then claim the order with UPDATE orders SET status = … WHERE id = $1 AND status = 'pending_payment'. If no row changed, something else already resolved it, so stop.
    Approved: order paid, coupon redeemed, cart checked_out.
    Declined: order failed. Lock the products in ID order, then add the quantities back. Coupon available, cart open.
    Commit. The key needs no change, because it already points to the order.
  2. Unknown: nothing to write. The order stays pending and holds its reservation.
  3. Respond: toCheckoutResponse(await loadOrderView(db, orderId)), built from the order as it is now: 201 paid, 202 pending, or 402 PAYMENT_FAILED. So if recovery got there first, the client still sees the truth.

If phase 3 itself fails with a 500 or 503 after the charge, the order stays pending. The key already points to it, so retries replay a 202 until the TTL passes. Then recovery resolves the order from the gateway's record, and the next retry replays the outcome.

Why pessimistic locks

OptionForAgainst
Row locks (chosen)Deterministic and explainable line by line. No retry loops. Contention is per product, which is fine at store scale.Locks are held for the length of the transaction. A hot product serializes its reserve phases, though never its payment calls.

SERIALIZABLE + retryThe database finds the conflicts itself.Serialization failures need a retry loop that has to be written and tested. Harder to predict in an interview.

READ COMMITTED is deliberate. After a lock wait, the waiter re-reads the newest row version and sees pending_payment or reserved, with no serialization error. At REPEATABLE READ those same points would raise 40001.

Lock order

TransactionLocks, in order
Reservekey (insert) → cart → products by ID → coupon. Step 8 then updates its own key row
finalizeOrdercart → order → products by ID (declines only) → coupon
Cart PUT / DELETEcart (then the cart_items write, whose FK check takes KEY SHARE on the product, which never conflicts)

Why nothing can deadlock. Every transaction that takes more than one row lock takes cart, then products by ID, then coupon, in that relative order. The key row can't be part of a cycle, for two reasons:

  • Only the reserve that inserted a key ever writes to it. Nothing writes a key after its transaction commits.
  • A conflicting claim takes no row lock. ON CONFLICT DO NOTHING waits only while an insert of the same key is still uncommitted, and at that moment the claim is the waiter's first statement, so the waiter holds nothing.

lock_timeout is set on the pool (new Pool({ lock_timeout }), from LOCK_TIMEOUT_MS, default 5 seconds). It covers every lock wait, including the claim and the advisory lock. A timeout becomes 503 LOCK_TIMEOUT.

Pending recovery

A pending order can come from an unknown outcome (a 202), from a crash between reserve and finalize, or from a phase 3 failure. In each case it holds stock and maybe a coupon. Once it is older than PAYMENT_PENDING_TTL_SECONDS (compared with now() in SQL against orders.created_at), resolvePendingOrder(orderId) can resolve it:

  1. Zero total: the order was never going to be charged, so resolve it as approved without calling the gateway.
  2. Otherwise, ask the gateway: gateway.retrieve(orderId), outside any transaction.
    Approved or declined: that is the resolution.
    Not found: call gateway.cancel(orderId). It returns cancelled, and from then on any late charge() for this order is declined. Or, if the charge landed in between, it returns that charge's result. Cancelled resolves as declined, with reason abandoned.
    The gateway throws: leave the order pending and try again later.
  3. finalizeOrder(orderId, resolution). Its conditional update makes every race safe: recovery against the original phase 3, and two recoveries at once, both change the order exactly once (I13).

findStalePending(db, ttl, s):
  orders o LEFT JOIN coupons c ON c.id = o.coupon_id
  WHERE o.status = 'pending_payment'
    AND o.created_at < now() - make_interval(secs => $ttl)
    AND ( s.scope = 'all'
       OR o.cart_id = $cartId
       OR c.code = $couponCode
       OR EXISTS (SELECT 1 FROM order_items oi WHERE oi.order_id = o.id AND oi.product_id = ANY($productIds)) )

The scope is a discriminated union, so a caller that forgets a filter fails to compile. Without it, the call would silently resolve every stale order. Recovery never holds a connection while it waits on the gateway, and it never runs inside another transaction: run inside a PUT's transaction, it would wait on the cart lock that transaction already holds. The cancel step is what makes I7 independent of timing. A charge slower than the TTL is declined rather than landing on stock that was already released.

Fake gateway

There is no off-the-shelf fake. Stripe's test mode needs a secret key, network access and an account, and the brief forbids depending on private services or credentials. It is also rate limited and can't produce a timeout on demand. stripe-mock is offline but stateless, and its README says it returns success instead of errors. Stripe's own guidance for automated tests is to mock the gateway's responses. So we write a small fake, shaped like Stripe:

interface PaymentGateway {
  charge(input: { orderId: string; amountPaise: number; paymentToken: string }, signal: AbortSignal): Promise<ChargeResult>
  retrieve(orderId: string): Promise<ChargeResult | { outcome: 'not_found' }>
  cancel(orderId: string): Promise<ChargeResult | { outcome: 'cancelled' }>
}
type ChargeResult =
  | { outcome: 'approved'; paymentRef: string }
  | { outcome: 'declined'; reason: string }

type Resolution =
  | { outcome: 'approved'; paymentRef: string | null }
  | { outcome: 'declined'; reason: string }

charge() throwing means the outcome is unknown. Resolution is what finalizeOrder takes: paymentRef is null for a zero total, and recovery maps cancelled to declined with reason abandoned. The gateway is a typed in-process interface, so its results are not zod-parsed. A real HTTP adapter would parse them at its own boundary.

  • The pm_card_* names are Stripe's own test tokens. The tok_timeout_* names are ours, because Stripe has no equivalent.
  • Charges are stored in an in-memory Map keyed by orderId. A repeated charge() returns the recorded result, so nothing is charged twice. cancel() writes a tombstone if nothing is recorded yet, or returns the recorded result if a charge exists. Each operation is a synchronous check-and-set on the map, so the two can't interleave.
  • Restarting the process loses the records, so retrieve() returns not_found and recovery cancels and releases. That is acceptable for a fake, and documented.
  • Test-only control lives in test/helpers/gate.ts, not in the source. It is a decorator: gated(fake, { at: 'before' | 'after' }) holds charge() either before the fake records the charge or after. It exposes an entered promise and a release() function, and it honours the abort signal.

Idempotency

  • Idempotency-Key is required, 1–255 characters. A missing, empty or over-long key gets 400 IDEMPOTENCY_KEY_INVALID.
  • request_hash = SHA-256 of JSON.stringify([cartId, couponCode ?? null, expectedTotalPaise, paymentToken]), computed on the values after zod has parsed and normalised them. Because the cart ID is part of the hash, a key reused on another cart is a mismatch.
  • Keys are global (there is no auth to scope them by) and are kept forever. Both are deferred.
  • The rule follows Stripe. Once a request has begun executing, its outcome is final. Requests that fail validation, or that conflict with another payment still in flight over the same cart or coupon, store nothing.

Coupons

Configuration, read from the environment and validated with zod at boot:
  • COUPON_EVERY_N_ORDERS (n): an integer ≥ 1
  • COUPON_PERCENT_OFF (x): an integer from 1 to 100
  • PAYMENT_PENDING_TTL_SECONDS: default 300
  • GATEWAY_TIMEOUT_MS: default 10000
  • LOCK_TIMEOUT_MS: default 5000
  • DATABASE_URL, PORT
The schema rejects a TTL below 10 × the gateway timeout.

Milestones

paid_orders        = COUNT(orders WHERE status = 'paid')
reached_milestones = floor(paid_orders / n)
next_milestone     = COALESCE(MAX(coupons.milestone), 0) + 1
eligible           = next_milestone <= reached_milestones

Generation runs in one transaction that starts with pg_advisory_xact_lock(<constant>), so concurrent generations queue rather than all computing the same milestone. Five parallel calls with two unrewarded milestones produce two coupons and three 409s, not one coupon and four false 409s. UNIQUE (milestone) is the guarantee (I9). Reading the count at READ COMMITTED is safe because paid orders are never un-paid (I13), so a stale count can only under-report eligibility.

Milestones come from the count of paid orders, not from a sequence. A Postgres sequence leaves gaps when a transaction rolls back, so it would count failed checkouts.

Codes take the form SAVE{x}-M{k}-{8 chars}. The 8 characters come from the uppercase Crockford base32 alphabet, so a code survives the shared couponCodeSchema (trim, uppercase) that the checkout body, the preview query and findStalePending all use. They are inserted with ON CONFLICT (code) DO NOTHING, and a collision retries with a fresh suffix, up to 3 times. The random part means a bearer code can't be guessed from its milestone.

Money and rounding

  • Money is an integer number of paise, end to end. No float appears in any money path. The API sends *Paise integers only.
  • Every paise column is bigint, read with { mode: 'number' }. Aggregates are cast with ::bigint and .mapWith(Number), because node-postgres returns int8 and numeric as strings. Capping quantity at 1000 keeps every value far below 253.
  • line_total = unit_price * quantity, and subtotal = sum(line_totals). These are exact.
  • discount = floor(subtotal * percent_off / 100), in integer arithmetic. One rounding step, applied once, at order level. It always rounds down, so it favours the store by under one paisa, and the same inputs always give the same result. The cart preview uses the same function.
  • total = subtotal - discount. With percent_off <= 100 the total is never negative, and CHECKs back that up (I10). A total of 0 is never charged.
  • Allocating the discount to individual lines (needed for partial refunds) is deferred.

Error model

The code is a stable contract that clients branch on, the message is for humans, and details carries what a client needs to recover. The HTTP status gives the class of problem: 400 for a malformed request, 402 for a failed payment, 404 for an unknown resource in the path, 409 for a conflict with current state, 422 for a well-formed request that is semantically invalid, and 503 for a transient condition that is safe to retry. onError builds every response with toErrorBody(err), the same builder completeKeyWithError uses, so a stored error and a live error can't differ.

  • Hono's 400 HTTPException for malformed JSON becomes VALIDATION_ERROR. Any other HTTPException becomes 500 INTERNAL.
  • A database error is recognised as err instanceof DrizzleQueryError. Its err.cause is then safe-parsed with { code: z.string(), constraint: z.string().optional() }. 55P03 becomes 503, and anything else becomes 500.
  • Business conflicts never reach the mapper, because explicit checks raise them first. The constraints are backstops.

Reporting

GET /admin/report runs in a single READ ONLY transaction at REPEATABLE READ. Every number comes from the same snapshot, so a checkout committing mid-report can't make gross revenue include an order that the order count leaves out. Only paid orders count as sales. The report never resolves pending orders.

{
  "paidOrders": 12,
  "ordersByStatus": { "paid": 12, "pending_payment": 1, "failed": 2 },
  "quantityByProduct": [{ "productId": "p_lamp", "name": "Limited Edition Desk Lamp", "quantity": 3 }],
  "grossRevenuePaise": 0,     // SUM(subtotal_paise) over paid orders
  "discountsPaise": 0,        // SUM(discount_paise) over paid orders
  "netRevenuePaise": 0,       // SUM(total_paise) over paid orders  == gross - discounts
  "coupons": { "generated": 3, "available": 1, "reserved": 1, "redeemed": 1 },
  "milestones": { "n": 5, "reached": 2, "rewarded": 2, "unrewarded": 0 }

Quantities are summed from order_items of paid orders, grouped by product_id, with the name taken from the current product row. Reconciliation means four things hold:

  • summing GET /admin/orders?status=paid gives exactly these figures;
  • redeemed coupons equal paid orders that have a coupon_id;
  • reserved coupons equal pending orders that have a coupon_id;
  • ordersByStatus matches the list.

The two endpoints are separate requests, so they reconcile only when no writes are running between them, and the test asserts that only at quiescence.

Test plan

Infrastructure

  • Database: a separate checkout_test database in the same Docker container, created by an initdb script. globalSetup zod-parses DATABASE_URL, refuses to run unless the database name ends in _test, and runs the migrations once.
  • Isolation: fileParallelism: false, because the files share one database. TRUNCATE … RESTART IDENTITY CASCADE plus a reseed before every test. afterEach releases every gate and awaits every in-flight request before truncating. Each pool closes in afterAll.
  • The app: each file builds createDb(testConfig) and calls createApp({ config, gateway, db }) through app.request(), with no server running. Each test gets a fresh FakeGateway.
  • Test config: it must pass the boot schema: LOCK_TIMEOUT_MS = 10000, GATEWAY_TIMEOUT_MS = 60000, a TTL of 600 seconds, and n = 2 where milestones matter. T15 and T17 alone build a second db and app with LOCK_TIMEOUT_MS = 200.
  • Pool size: the test pool's max is at least the fan-out + 2. A gated request holds no connection, so this stays correct.
  • Lock barrier (test/helpers/barrier.ts):
    • A dedicated connection opens a transaction and locks the target: a row with FOR UPDATE, or the advisory lock. The test fires N requests.
    • A separate autocommit connection polls pg_stat_activity, filtered on datname = current_database() and excluding the barrier and poller PIDs, until N backends show wait_event_type = 'Lock'. On timeout it throws BarrierTimeout.
    • Then the barrier commits.
    • Each test records which statement blocks on the barrier, both with the enforcement present and with it removed.
  • holdLock(target) takes the same lock but releases only when the test calls release(). It is used where a request must time out (T17).
  • Gate (test/helpers/gate.ts): see Fake gateway. A gated test awaits entered, then awaits the N−1 losers (with a bound), then runs the idle-in-transaction check excluding the barrier and poller PIDs, and only then releases. It never Promise.alls a gated request before releasing it.
  • Clock: every time comparison uses the database's now(). Tests backdate relative to the row (created_at - interval '1 day') and never pass a JavaScript Date, since the Docker VM clock can drift.
  • Assertions: every concurrency test asserts the exact status counts and zero 500s, because the database backstops would otherwise hide a missing lock. While a gate is held, no backend may be idle in transaction, which directly catches a charge made inside a transaction.
  • Repeats: the concurrency file runs about 20 times once, using Vitest's repeats option. Check that beforeEach re-runs on each repeat in the installed version. Never use retry.

  • Removing the savepoint alone fails no test, because every check already runs before every write. It is defence in depth.
  • A single ANY($1) FOR UPDATE without ORDER BY probably won't deadlock either, because both transactions scan in the same order. So T7 guards against a lock-per-line loop, and does not prove the need for ORDER BY.

A race whose outcome is a set, not a single result. A key retried while the original request's finalize is running gets 202 if finalize hasn't committed yet, or the final 201 or 402 if it has. Any test that can hit this race asserts that the result is in that set.

Multiple instances and production scale

  • Correctness holds with N instances. Every invariant lives in Postgres: locks, constraints and transactions. No in-process state, mutex or cache is involved. The one exception is the fake gateway's in-memory store, which is per process. A real PSP is external and shared, so the exception goes away with it.
  • A real PSP: keep the same three phases.
    • Stripe can cancel only a PaymentIntent that already exists. So the adapter creates the PaymentIntent first, with orderId as its idempotency key, stores its ID on the order, and only then confirms it. cancel() targets that stored ID, which closes the intent even if the confirm request never arrived.
    • Make the PSP's webhook the main way a pending order gets resolved, with retrieve() as the fallback.
    • Run reconcile on a schedule as well as lazily.
  • Downstream side effects (receipt emails, an OrderPaid event for analytics or fulfilment): this is where the transactional outbox comes in. finalizeOrder writes an outbox row in the same transaction that marks the order paid, and a relay delivers it at least once to idempotent consumers. Brandur's design pairs the same way, with a "transactionally staged job drain" for receipts.
  • Hot products: per-row locks serialize the reserve phase for one SKU. Payment calls hold no locks, so this lasts only milliseconds. At flash-sale scale, move to a stock-reservation table or partitioned counters.
  • Report: SUM over all orders gets slow over time. Fix it with counters updated in finalizeOrder, or with a read replica.
  • Idempotency keys: scope them per client or API key once auth exists, and add a retention window.
  • Pool sizing: lock waits hold connections, so set the pool size and lock_timeout together.

Intentionally deferred

  • Auth and real admin protection
  • A real PSP adapter and webhooks
  • Refunds and cancellations, which would break I13 and need per-line discount allocation
  • Cart expiry, and reserving stock at add time
  • Retention and per-client scoping of idempotency keys
  • Multi-currency, tax, and minimum charge amounts
  • Pagination on the admin lists
  • An OpenAPI spec (a .http file instead)
  • Frontend
  • Changing n after milestones exist
  • An outbox, until there are downstream side effects
