Implementation Plan

Seven GitHub issues that build the design in architecture.html (v4). Each issue is a vertical slice: it owns its schema migration, routes, error codes, tests and docs, and when it merges, the service works end to end for everything built so far. Test IDs (T1–T31) and invariant IDs (I1–I15) refer to architecture.html.

Principles

Vertical, not layered

No "all the schema" or "all the tests" issue. Each issue ships a behaviour a reviewer can exercise over HTTP and prove with its own tests.

No cross-stacking

An issue builds only on merged issues, and nothing is reopened later. Where a later issue extends earlier code, the extension is additive (a new branch, a new trigger) and is listed in that later issue.

Self-contained and repeatable

Each issue brings its own migration, seed changes, fixtures and test helpers. Migrations and seeds can be re-run safely, and every test truncates and reseeds, so tests can run in any order, any number of times.

Docs travel with code

Each issue updates the README endpoint table, requests.http, its own DECISIONS.md sections, and the mutation log for its tests. The last issue only finishes and verifies the docs.

Definition of done (every issue)

  • The issue's tests pass, and so does the whole suite (pnpm test against Docker Postgres). No test is skipped or marked .todo.
  • Any schema change is a new Drizzle migration. Its generated SQL has been read, and earlier migrations are untouched.
  • Every new route validates params, query, headers and body with zod, and every new error code is in the ERRORS table.
  • The README endpoint table lists each new route with its request, response, status codes and errors. requests.http has a runnable example for it.
  • DECISIONS.md has the issue's decisions in the Context / Options / Choice / Why / Consequences shape, and the mutation log has a row for each of the issue's concurrency and payment tests: "removed X, then test Y fails with Z".
  • The PR title is a conventional commit, and the PR body says Closes #N and includes a test plan.

[01] Foundation: scaffold, products, error model, test harness

Size MNeeds: nonePR: feat(api): scaffold service with products and error model

Goal: a running service that lists products and lets an admin edit one, with the error envelope, validation, config and test harness that every later issue uses.

Build

  • Tooling: Node 22, TypeScript, pnpm, Hono, Drizzle, zod and Vitest. docker-compose.yml runs Postgres 16, and an initdb script also creates checkout_test.
  • config.ts: the full env schema (n, x, the TTL, the gateway timeout, the lock timeout, DATABASE_URL, PORT), including the rule TTL ≥ 10 × gateway timeout. It's done now, so later issues never touch it.
  • db/client.ts: createDb(config) → { db, pool }, with lock_timeout set on the pool.
  • Migration 0001: products. seed.ts loads the 5 seed products with an upsert, so it is safe to re-run.
  • errors.ts:
    • the ERRORS table, AppError(code, details) and toErrorBody;
    • onError, including the DrizzleQueryError mapper (55P03 → 503);
    • the envelope's notFound handler;
    • a custom zValidator hook, and the Content-Type check.
  • app.ts: createApp({ config, gateway, db }) mounts router factories. server.ts boots it.
  • domain/money.ts: lineTotal, discount and total, all in integer paise.
  • Routes: GET /products, and PATCH /admin/products/:id with a strict schema needing at least one field.
  • Test harness:
    • globalSetup refuses any database not named *_test, then runs the migrations;
    • fileParallelism: false;
    • test/helpers/db.ts (truncate + reseed) and test/helpers/app.ts.

Errors introduced

VALIDATION_ERROR, PRODUCT_NOT_FOUND, NOT_FOUND, INTERNAL, LOCK_TIMEOUT

Tests

  • T27 money unit tests: the cable at 34999 with 10% off, 100%, never negative.
  • T29 config it.each.
  • T25, this issue's rows: a malformed product ID, an unknown product on PATCH, an empty PATCH, a non-JSON Content-Type, malformed JSON, and an unknown route returning 404 inside the envelope.
  • PATCH changes the price, name and stock, and GET /products reflects it.

Docs

[02] Carts: create, view, set and remove items

Size MNeeds: 01PR: feat(carts): cart lifecycle with set-quantity semantics

Goal: a client can build and inspect a cart, and every cart mutation is safe to retry and safe under concurrency.

Build

  • Migration 0002: carts (with all three status values), and cart_items (quantity 1–1000, PK on cart and product).
  • Routes: POST /carts, GET /carts/:id, PUT /carts/:id/items/:productId, DELETE /carts/:id/items/:productId.
  • PUT and DELETE lock the cart FOR NO KEY UPDATE and require status = 'open'. That one guard covers both checked_out and pending_payment.
  • PUT: a soft stock check, with 201 or 200 decided by a SELECT made under the cart lock, then an INSERT or an UPDATE.
  • DELETE of an absent line returns 200.
  • Cart view: live prices, available, subtotalPaise, and discountPaise: 0 with totalPaise = subtotal. Those last two fields exist now so that 04 only adds a preview.
  • Test helper: test/helpers/barrier.ts, with the barrier (row or advisory lock, polled from a separate autocommit connection) and holdLock.

Errors introduced

CART_NOT_FOUND, CART_CHECKED_OUT, CART_PAYMENT_PENDING, INSUFFICIENT_STOCK

Tests

  • T8: 5 concurrent identical PUTs behind a FOR UPDATE barrier on the cart give {201:1, 200:4}.
  • T24, this issue's rows: delete an absent line, PUT above stock, odd-paise totals, and available:false after a PATCH. Both locked statuses get rejected, with each status set directly in SQL. The end-to-end versions arrive with 03.
  • T25, this issue's rows: quantity 0, −1, 1.5, "2" and 1001; a malformed cart ID; an unknown cart on GET, PUT and DELETE; an unknown product on PUT.

Docs

README for the four routes, and the requests.http cart walkthrough. DECISIONS.md: PUT set-quantity with an idempotent DELETE, the soft stock check, and the 1000 quantity cap.

Not in this issue

The coupon preview (04), and recovering stale orders before a mutation (05).

[03] Checkout: reserve, charge, finalize, with idempotency keys

Size LNeeds: 02PR: feat(checkout): idempotent three-phase checkout with fake gateway

Goal: a cart can be checked out exactly once. Retries, concurrent checkouts, declines and business failures all behave as the architecture specifies, and stock never oversells. This is the core of the assignment.

Build

  • Migration 0003:
    • orders, without coupon columns: discount_paise is always 0 here, and 04 adds the coupon columns;
    • order_items, and idempotency_keys (with no state column);
    • the partial unique index on the live order per cart;
    • all the order, line and key CHECKs.
  • Payments module: modules/payments/gateway.ts holds PaymentGateway with charge(), ChargeResult and Resolution. fake-gateway.ts implements pm_card_visa, pm_card_chargeDeclined, pm_card_chargeDeclinedInsufficientFunds and the unknown-token decline, and charges are idempotent per orderId.
  • checkout/idempotency.ts: claimKey (ON CONFLICT DO NOTHING, then a separate load), the request hash, completeKeyWithError, and replay from the order or from the stored response.
  • checkout/service.ts:
    • reservePhase: steps 1–8 with the savepoint, the final and transient handling, products locked ORDER BY id FOR NO KEY UPDATE, and the required price guard;
    • phase 2, with AbortSignal.timeout;
    • phase 3: approved or declined goes to finalizeOrder; unknown, meaning any thrown error, returns 202 with Retry-After.
  • payments/finalize.ts: finalizeOrder, with the conditional claim on the order and the product restore in ID order. It's written in full now, and recovery reuses it in 05.
  • orders/view.ts: loadOrderView, toOrderView and toCheckoutResponse. A new route, GET /orders/:id.
  • Test helper: test/helpers/gate.ts, the gated(fake, { at }) decorator with entered and release().

Tests

[04] Coupons: milestones, generation, preview and redemption

Size MNeeds: 03PR: feat(coupons): milestone coupons with preview and single redemption

Goal: an admin can generate a coupon once a milestone is reached. A customer can preview it on their cart and redeem it exactly once. A failed checkout never consumes it.

Build

  • Migration 0004:
    • coupons;
    • new orders.coupon_id and orders.percent_off columns;
    • the discount-formula CHECK and the coupon/percent pairing CHECK;
    • the partial unique index on the live order per coupon.
  • domain/milestones.ts: the eligibility math over paid orders.
  • coupons/code.ts: couponCodeSchema (trim, uppercase), and a generator using Crockford base32.
  • Routes:
    • POST /admin/coupons: an advisory lock, then the oldest unrewarded milestone, then ON CONFLICT (code) retries, returning remainingEligible;
    • GET /admin/coupons.
  • Additions to existing code:
    • Cart preview: ?couponCode= on GET /carts/:id. It succeeds only for an available coupon, and otherwise returns checkout's error.
    • Reserve: step 6 locks the coupon and sets it to reserved. couponCode joins the request hash.
    • Finalize: the coupon is redeemed on approval and made available again on a decline.
    • Order view: includes the coupon.

  • T19, the zero-total half: x = 100 gives a paid order with no gateway call.

[05] Pending payments: unknown outcomes, recovery and reconcile

Size LNeeds: 04Independent of 06PR: feat(payments): recover pending payments with cancel-before-release

Goal: a payment with an unknown outcome is held, never released while its charge could still land, and resolved after the TTL. That happens lazily on mutating requests, or through the admin reconcile.

Build

  • Fake gateway: the tok_timeout_approved and tok_timeout_declined tokens, which record, then throw. retrieve(), and cancel() with a tombstone: after a cancel, any charge is declined with cancelled.
  • payments/recovery.ts:
    • findStalePending, with the StaleScope union, the DB-clock TTL, and the cart, coupon and product clauses;
    • resolvePendingOrder: zero total resolves as approved; otherwise retrieve, then cancel on not found, then finalizeOrder.
  • Phase 0 hooks, which run outside any transaction:
    • checkout recovers by cart, coupon and products;
    • PUT recovers by cart and product;
    • DELETE recovers by cart.
    A failure recovering one order is logged and the request carries on.
  • Route: POST /admin/payments/reconcile, which catches failures per order and returns { resolved, stillPending }.

Errors introduced

None.

Tests

  • T10: two reconciles at once. Stock is restored exactly once.
  • T11: recovery against the original finalize. The timestamps don't change.
  • T12: a slow charge overtaken by recovery. The response is 402 with abandoned, and nothing is charged.
  • T14: a timeout, then a retry that gets 202, then a reconcile before the TTL that leaves it alone, then a reconcile after the TTL that makes it paid.
  • T15: every recovery trigger, on the 200 ms app.
  • T16: a crash after reservePhase. A retry gets 202, then reconcile runs, then a retry replays 402.
  • T19: the crashed zero-total half.
  • T30: the cancel and retrieve rows.
  • T31: stub gateways. A charge that lands between retrieve and cancel ends up paid. A retrieve() that throws leaves the order pending. One failure doesn't abort reconcile.

Docs

README for reconcile, and the 202 polling contract. requests.http covers a timeout followed by a reconcile. DECISIONS.md:

  • holding unknown outcomes;
  • cancel-before-release, and the timeout and TTL rule;
  • the recovery triggers, and why GET requests never trigger recovery;
  • the reconciler compared with Brandur's completer.

Not in this issue

A scheduled reconciler, and a real PSP adapter. Both are deferred and documented in 07.

Open questions

1. Is 03 too big?

03 holds reserve, idempotency, the gateway, finalize and the order view. It's the largest issue, but splitting it means building checkout and then rewriting it. For example, checkout without keys first means the claim (reserve's first statement) and the savepoint get retrofitted later. My proposal is to keep it as one issue.

2. Title format

Proposed: [01] Foundation: …. Alternatives are 01 · Foundation: … or a conventional-commit style title such as 01 feat(api): ….

3. "Idempotent in each way"

I read this as meaning each issue is self-contained: it can be implemented and reviewed on its own, its migration and seed are safe to re-run, and its tests pass in any order and any number of times. If you meant something else, for example that each issue's own scripts should be re-runnable, tell me and I'll adjust.
